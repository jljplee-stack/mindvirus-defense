## 1. 감시 대상을 고르는 법 — 인벤토리

정본 목록의 SOT(단일 진실)는 `$CANON_HOME/inventory.conf` 하나다.
씨앗은 `examples/inventory.example.conf` 이고, **경로를 사이트에 맞게 반드시 고쳐야 한다.**

> ⚠ `canon-verify.sh --list` 가 0건을 내면 그것은 "깨끗하다"가 아니라 **"아무것도 안 보고 있다"** 이다.
> 설치 직후 이 명령으로 전개 결과를 눈으로 확인하라. 이 킷에서 가장 조용히 실패하는 자리다.

### 1.1 tier 4종

| tier | 새 파일 추가 | 기존 파일 수정 | 삭제 | 쓰는 곳 |
|---|---|---|---|---|
| `strict` | ALERT | ALERT | ALERT | 지침·헌장·규약 — 정당 변경이 드문 것 |
| `append` | – | 순수 append=NOTICE / **기존 내용 변경=ALERT** | ALERT | 색인·원장형 정본 |
| `watch` | NOTICE | ALERT | ALERT | 장기기억 본문(디렉터리 재귀 `*.md`) |
| `watch-soft` | NOTICE | NOTICE | ALERT | 소음이 과할 때 내리는 스위치 |

### 1.2 ★`append` tier 가 이 설계의 핵심 발상이다

색인·원장형 정본은 **정당한 추가가 잦다.** 그런데 마인드 바이러스의 형태는
**"이미 있던 문장을 바꾸는 것"** 이다. 두 축은 다르다.

그래서 두 축을 분리해 판정한다 — **베이스라인 길이만큼만 다시 해시해서 앞부분 바이트가
그대로인지** 본다.
- 앞부분이 그대로면 = 순수 append → **NOTICE** (추가된 줄까지 경보문에 실어 보여준다)
- 앞부분이 바뀌었으면 = 전량 재기록·중간 수정 → **ALERT**

이 한 가지 구분이 "정상 운영 소음"과 "감염 신호"를 갈라 준다. 이것이 없으면 색인형 정본은
tier 를 뭘로 주든 쓸모가 없다 — `strict` 면 하루 종일 울리고, 안 넣으면 통째로 사각이 된다.

### 1.3 자기보호 — 감시자를 무력화하면 감시가 끝난다

`canon-*.sh` 5종과 `inventory.conf` 자신을 `strict` 로 인벤토리에 넣는다.
이것은 감시 범위의 "확장"이 아니라 **② 자신의 무결성**이다. 빼지 마라.

### 1.4 무엇을 넣지 **말아야** 하나

세션 상태 파일(진행 로그·TODO·수백 KB에 하루 여러 번 갱신)은 넣지 마라. 정본이 아니라
작업 상태다. 넣는 순간 경보가 하루 수십 건이 되고, **사람이 경보 전체를 무시하기 시작한다.**
경보 피로는 감시 체계를 죽이는 가장 흔한 사인이다.

## 2. 정당한 변경 확정 = 편집과 재서명을 **한 명령**으로

경보 피로를 만드는 두 번째 경로는 "고치고 서명을 깜빡했다"의 반복이다.
그래서 정당 편집의 입구를 **하나**로 만든다.

```
canon-edit.sh   <정본파일> --reason "<변경 근거>"   # 편집 → 자동 재서명 → 대조 (한 명령)
canon-resign.sh <파일>…    --reason "<근거>"        # 이미 편집했을 때
canon-resign.sh --attest   --reason "<검토 확인>"   # 해시 불변·검토 사실만 원장에 기록
canon-resign.sh --all      --reason "<근거>"        # 현재 불일치 전부
```

⚠**"트랜잭션"이라고 부르지 않는다.** `canon-edit.sh` 는 편집기가 원본을 **제자리에서** 고치게 하고
그 뒤에 재서명한다. 재서명이 실패하면 **바뀐 파일이 그대로 남는다**(그리고 그 상태는 다음 대조에서
경보로 드러난다). 롤백·스테이징·잠금이 없으므로 원자적이지 않다.
묶는 이유는 원자성이 아니라 **"고치고 서명을 깜빡하는 일"을 없애는 것**이다.
· 재서명이 실패했다면 그 자리에서 `canon-resign.sh <파일> --reason "…"` 을 다시 돌리거나,
  파일을 되돌려라. 방치하면 경보가 남는다.

### 2.1 `--reason` 은 필수다 (누락 시 exit 4)
**근거 없는 서명은 서명이 아니다.** 이 필드가 있어야 나중에 "이 변경이 왜 정당했나"를 되짚을 수 있고,
경보를 닫으려고 습관적으로 서명하는 것을 막는다.

### 2.2 원장과 스냅샷은 성질이 다르다
- **원장 `resign-ledger.jsonl` = append-only.** `open(...,'a')` 고정. 전량 재기록 API 금지.
  사후 수정이 가능한 원장은 원장이 아니다.
- **베이스라인 `baseline.tsv` = 현재 상태 스냅샷.** 원장이 아니므로 원자적 전량 교체(tmp+rename)가 맞다.

쓰기 순서도 정해져 있다 — **원장 먼저, 스냅샷 나중.** 중간에 죽으면 "기록은 있는데 스냅샷이
안 바뀐" 상태가 남는데, 그건 다음 대조에서 경보로 드러난다. 반대 순서면 **조용히 서명만 바뀐
상태**가 남는다. 실패했을 때 남는 잔여가 무해한 쪽을 골랐다.

### 2.3 행위자 게이트 — 재서명은 오케스트레이터 권한이다
`CANON_ROLE` 또는 `CANON_ROLE_CMD` 로 판정한 역할이 `CANON_DENY_ROLES` 에 걸리면 **거부(exit 5)** 한다.
역할 미상(사람이 직접 치는 셸)은 통과한다.

**왜 하위 노드가 재서명하면 안 되나**: 재서명은 "이 변경을 정당하다고 선언"하는 행위다.
하위 노드가 그것을 할 수 있으면, **자기가 넣은 문단을 자기가 정당화**할 수 있다.
그러면 이 체계는 감염을 탐지하는 도구가 아니라 **감염을 정당화하는 도구**가 된다.

### 2.4 부트스트랩 예외와 그 봉쇄
최초 `--rebuild` 는 베이스라인이 **아직 없을 때만** 역할 게이트를 면제한다 —
최초 서명은 "변경 승인"이 아니라 "현재 상태 촬영"이기 때문이다.

★그런데 그것만으로는 구멍이 남는다. **하위 노드가 베이스라인 파일을 지우고 다시 부트스트랩하면
무단 변경을 세탁할 수 있다.** 그래서 봉쇄를 하나 더 두었다:

> **원장에 `attest` 기록이 한 번이라도 있으면 부트스트랩 면제는 닫힌다.**
> 원장은 이 킷의 API 로는 append 만 되므로, 이 스크립트를 지나는 경로에서는 봉쇄가 풀리지 않는다.

⚠**조건을 정확히 적는다**: "append-only" 는 **이 킷의 쓰기 API 가 append 모드만 쓴다**는 뜻이지,
파일시스템이 삭제를 막는다는 뜻이 아니다. 원장 파일을 지울 수 있는 주체는 봉쇄도 함께 지운다.
그 경로가 어떻게 열려 있고 무엇으로 좁히는지는 `docs/LIMITS.md` §6 에 전부 적었다.

이 성질과 **"attest 전에는 허용된다"는 대조군**을 둘 다 강제로 돌려 확인했다
(`tests/cycle-drill.sh` 18·19단계). 봉쇄를 주장할 때 봉쇄되는 쪽만 보이면 아무것도 증명하지 못한다 —
**허용되는 쪽도 함께 보여야** 그 봉쇄가 실제로 작동한 것이다.

## 3. 경보 설계 — 재발화 억제와 해소 판정

### 3.1 지문
지문 = `kind|path|실측해시`. **같은 지문은 평생 1회만 발신한다.**

⚠**정확히는 "1회 발신 시도"다.** 상태 파일에 지문을 기록하는 시점이 **전송보다 앞**이고,
전송 명령의 종료코드를 검사하지 않는다. 따라서 **경보 채널이 죽어 있으면 그 경보는 영구히 유실된다**
(다음 실행에서는 이미 보낸 것으로 억제된다). 채널 스크립트가 실패를 알리도록 만들고
(예시 4종 중 메일·Slack 은 실패 시 0이 아닌 값을 낸다), **채널 자체의 생사를 따로 감시하라.**
해시가 *또* 바뀌면 새 지문 → 새 경보가 나간다(변조가 진행 중이라는 신호이므로 알려야 한다).

★억제기가 "아무것도 안 울리는 것"이 아님을 증명하는 대조를 드릴에 넣었다 —
같은 상태 재실행은 억제(1건 유지), 추가 변조는 새 경보(2건). 둘 다 봐야 억제기가 살아 있다는
증거가 된다(`cycle-drill.sh` 8·9단계).

### 3.2 경보 본문에 반드시 들어가는 것
파일 경로 · **기대(서명) sha256** · **실측 sha256** · **마지막 정당 서명 시각** · 판정 사유 ·
해소 방법 2가지 · 전체 대조 명령. 경고 머리표는 **첫 줄**에 둔다(각주에 묻으면 읽히지 않는다).

### 3.3 ★해소 판정 — 명시하지 않으면 경보는 영원히 남는다
**해소 = 그 경로에 finding 이 하나도 없는 상태.** 도달 경로는 둘뿐이다.

1. 오케스트레이터가 재서명한다 → 베이스라인이 현재를 인정
2. 파일을 원래 내용으로 되돌린다 → 해시가 베이스라인과 재일치

**무시·시간 경과·재시작으로는 절대 해소되지 않는다.** 해소되면 【해소】 한 줄을 발신하고 상태를 지운다.
같은 경로에 다른 finding 이 남아 있으면 해소로 치지 않는다.

> 경보에 해소 조건이 없으면 보드가 거짓말을 시작한다. 발화만 있고 해제가 없는 경보는
> 시간이 지나면 전부 "빨간 채로 방치된 것"이 되고, 사람은 색을 보지 않게 된다.

### 3.4 종료코드
`0` clean · `1` NOTICE · `2` ALERT · `3` **판정 불가**.
★`3` 도 사건으로 취급해 발신한다(`CANON_ALERT_LEVEL=BROKEN`) — **감시가 조용히 죽는 것이
가장 나쁘다.** 인벤토리 오류·베이스라인 부재·대조기 자신의 훼손이 여기로 온다.

### 3.5 경보 채널은 한 변수로 갈아 끼운다
```
CANON_ALERT_CMD="<명령>"     # 본문은 stdin, 등급은 CANON_ALERT_LEVEL 환경변수
```
비워 두면 `$CANON_ALERT_LOG` 파일에 append 한다(설정 0으로도 돈다).
예시 4종이 `examples/alert-cmds/` 에 있다: 파일 · 표준출력 · Slack 웹훅 · 메일.
사내 통보 도구가 있으면 그것을 그대로 넣으면 된다.

⚠ 경보 본문에는 **파일 경로와 해시**가 들어간다. 그 자체가 조직 내부 정보다. 공개 채널로 보내지 마라.

## 4. 상주 배선 — **독립 프로세스를 권한다**

이미 돌고 있는 다른 감시기에 이 관심사를 얹지 마라.

| | (a) 기존 감시기에 배선 | **(b) 독립 스케줄 (권고)** | (c) 오케스트레이터 세션이 감시 |
|---|---|---|---|
| 가동 중 자산 수정 | ⚠필요 | **0** | 0 |
| 실패 반경 | ⚠그 감시까지 같이 죽는다 | 자기 프로세스만 | 세션 죽으면 같이 죽음 |
| 사람 부재 시 | 동작 | **동작** | ⛔정지 |
| 재부팅 생존 | 동작 | **동작** | ⛔수동 재개 |

**(c)를 배제하는 결정적 이유**: 사람이 자리를 비운 국면이 정확히 위조·오작동이 나타나는 국면이다.
그 국면에 꺼져 있는 감시는 감시가 아니다.

비용은 무의미하게 작다 — 참조 실측 **60ms/회 · 156파일 0.7MB**. 300초 주기여도 CPU 점유는 0.02%다.

배선 예시는 `examples/scheduler/`(launchd · systemd timer · cron).
⚠ **launchd `StartInterval` 과 cron 은 기계가 자는 동안의 발화를 통째로 놓친다**(따라잡지 않는다).
자주 자는 노트북이라면 그 공백이 곧 사각이다 — systemd timer 의 `Persistent=true` 를 쓰거나
상시 가동 서버에 두는 편이 낫다.

## 5. 층 ③ 쓰기 가드

### 5.1 무엇을 막나
에이전트 도구 호출의 PreToolUse 훅으로 `Write|Edit|MultiEdit|NotebookEdit|Bash` 를 검사하고,
**정본 경로에 대한 쓰기**를 거부한다. **읽기는 막지 않는다** — 하위 노드는 지침을 읽어야 한다.

⚠**도구 이름은 플랫폼 계약이다.** 판정 함수는 방어적으로 `Update` 라는 이름도 함께 보지만,
**matcher 에 없는 도구에는 훅이 아예 발화하지 않는다.** 당신 에이전트가 다른 이름
(`write_file`·`execute_command` 등)을 쓴다면 matcher 와 판정 함수를 **그 이름으로 바꿔야 한다** —
안 바꾸면 이 층은 조용히 0층이 된다. `docs/LIMITS.md` §9.

Bash 는 문자열이 아니라 구조로 본다: 리다이렉션 대상 · `tee` · `rm/mv/cp/dd/truncate/chmod` 목적지 ·
`sed -i` 대상 · 인터프리터 인라인 코드 · 셸 탈출 구문(`bash -c`·`eval`·`$()`·백틱·`xargs`).
정본을 **읽어서 딴 데 쓰는 것**(`grep 정본 > /tmp/out`)은 통과시킨다 — 대상만 본다.

⚠**"구조로 본다"의 범위는 좁다.** 분석기는 세그먼트의 **첫 토큰**을 명령으로 간주한다.
따라서 앞에 환경변수 할당(`LANG=C tee …`)이나 래퍼(`env tee …`·`command tee …`)가 붙으면
**실제 명령을 보지 못하고 통과시킨다.** `sed --in-place` 처럼 긴 옵션 표기도 마찬가지다.
전수 목록은 `docs/LIMITS.md` §1. **이 층은 보안 경계가 아니라는 말은 이런 뜻이다.**

### 5.2 보호 목록이 인벤토리보다 **의도적으로 넓다**
②는 **탐지**라 정밀해야 소음이 안 나고, ③은 **예방**이라 넓어야 샌 곳이 안 생긴다.
정본 디렉터리를 통째로 막아도 하위 노드의 정상 작업에는 지장이 없다
(자기 TODO·프로젝트 소스·작업 메모는 전부 통과 — self-test A군 14케이스가 그것을 지킨다).

목록의 SOT = `$CANON_PROTECTED` 파일. 없으면 인벤토리에서 파생한다(글롭·디렉터리는 디렉터리로 넓혀서).
`canon-init.sh --protected` 가 파생본을 만들어 준다. **손으로 더 넓혀도 된다.**

### 5.3 fail 정책
python 부재·JSON 파싱 실패 → **보호 경로 문자열이 입력에 보이면 거부**(canon 한정 fail-closed),
안 보이면 통과(무관 작업 과차단 방지).

## 6. 검증 방법론 — 이 킷이 자기 주장을 어떻게 증명하나

1. **자체 배터리**(`--self-test`) — 각 스크립트가 자기 판정 함수를 검사한다. 총 68 케이스.
   설정 없이 킷 상태 그대로 돌아야 한다.
2. **전 사이클 실동작 검증**(`tests/cycle-drill.sh`) — 스크립트들을 **실제 프로세스로 이어 붙여**
   운영과 같은 경로를 돌린다. 19단계.
   **안 돈 경로는 미검증 코드다** — 자체 배터리가 초록이어도 배선이 끊겨 있을 수 있다.
3. **음성 대조군** — 무언가를 "막는다"고 주장할 때, 막히는 쪽만 보이면 아무것도 증명되지 않는다.
   **허용되는 쪽을 함께** 보여야 그 판정기가 살아 있다는 증거가 된다.
   이 킷의 대조군 3쌍:
   - 억제됨(같은 상태) ↔ 새 경보(추가 변조)  → 억제기가 눈이 먼 것이 아니다
   - 차단(정본 쓰기) ↔ 통과(작업 파일·정본 읽기) → 가드가 전부 막는 것이 아니다
   - 거부(attest 후 재부트스트랩) ↔ 허용(attest 전 최초 촬영) → 봉쇄가 attest 때문이다
4. **모델 개입 0** — 모든 판정은 종료코드와 파일 내용으로만 한다.
   에이전트가 "그건 하면 안 됩니다"라고 말하는 것은 증거가 아니다.

실행 로그는 `evidence/` 에 있다.
